# 03 — Model, training, generation, filtering and regimes

Revised 2026-10-12 (design review). Everything here is implemented in `harness/run_chain.py` and `harness/metrics.py`; the config is `configs/chains.yaml`.

## 1. Base model (≤ 300M parameters; verified 2026-10-12)

| Role | Model | Why | Check |
|---|---|---|---|
| SUBWORD (the study) | `google/gemma-3-270m` (268M parameters: 170M embeddings for a 262k-entry multilingual tokenizer + 100M transformer) | smallest current multilingual pretrained model with Bangla coverage; base checkpoint, not instruction-tuned | Gemma licence accepted on the `HF_TOKEN` account (done 2026-10-12); `transformers >= 4.56`; **bfloat16 only**: the model is bf16-trained, float16 overflows and vLLM refuses `gemma3` in float16 |
| fallback | `HuggingFaceTB/SmolLM2-360M` | only if gemma-3-270m fails Gate 2 validation; English-centric, exceeds the cap slightly; needs a DECISION and a deviation note | — |

The untouched base model is evaluated first (`run_chain.py --base EN/BN`: chain ids `BASE-EN`, `BASE-BN`, generation −1) so the starting level of each language is on record. Model id, revision, tokenizer hash and licence go to every `step.json`.

## 2. Training recipe (identical across chains)

- Full fine-tuning; bfloat16 autocast with fp32 master weights; AdamW (β = 0.9/0.95, weight decay 0.1); learning rate 2e-4, 3% warm-up, cosine decay to 10% of the peak (`cosine_with_min_lr`); one epoch over the generation's training set; sequence length 1,024 with packing (documents separated by EOS); effective batch 64 sequences (micro-batch 8 × 8 accumulation; micro-batch 4 is the OOM fallback with the effective batch unchanged); gradient clipping 1.0; gradient checkpointing on.
- **Initialisation.** Generation 0 trains the base model on the real seed corpus (10M tokens). Generation g ≥ 1 starts from the generation g−1 checkpoint of its own chain (warm-start chaining, with a fresh warm-up/cosine cycle each generation). This is the stated design; re-initialisation from the base model at every generation is scoped out.
- **Prefix masking.** A synthetic document is stored as its real 12-word prefix (token ids) plus the generated continuation. During training the prefix tokens are fed as context but carry label −100, so the loss is computed on generated tokens only (REPLACE trains on 100% generated targets; `training.prefix_mode: masked`). `step.json` records real, synthetic and masked target tokens. Every training document starts with gemma's `<bos>` token (context, label −100, not counted as a target), as do the generation prompts and the scorer's inputs: without it gemma-3 degenerates (2026-10-13 base-model A/B in `logs/decisions.md`). Documents are packed into `seq_len` blocks with `<eos>` between them. `<eos>` is a training target only after a document that really ended: a continuation the model stopped itself, or a real document that was not cut (by the corpus builder's 1,024-token limit or by `seq_len`). After a cut it is context only (label −100), because the generator never produced it. This was fixed on 2026-10-14 after the G3 pilot read; before the fix, REPLACE generation 1 learned to end documents at the generation length cap (`results/deviations.md`).
- **Seeds.** seed = 20261010 + seed_offset + g (seed_offset 0 for the confirmatory chains, 1000/2000 for the re-seeded pairs), used for packing order, trainer and generation.
- **Checkpoints** are saved in bfloat16 (0.54 GB each) and loaded as fp32 master weights by the next generation; every checkpoint is archived (`11_TEARDOWN_CHECKLIST.md`).
- Memory on the RTX 4090 (24 GB): weights + gradients + Adam states ≈ 4.3 GB in fp32, plus activations and the 262k-vocabulary logits at micro-batch 8 × 1,024 with checkpointing; fits, with micro-batch 4 as the fallback.

## 3. Regimes (what generation g ≥ 1 trains on; budget B = 10M generated tokens)

| Regime | Training set for generation g | Chains |
|---|---|---|
| REPLACE | the B synthetic tokens generated by the generation g−1 model (prefixes masked) | confirmatory; -s2, -s3, -WM, -topp95 |
| ACCUMULATE | real seed corpus + all synthetic corpora from generations 1…g−1 + the new synthetic corpus from g−1; one epoch over the union (training time grows with g; the dataset and the number of optimizer steps grow linearly, which is stated as part of the regime) | confirmatory |
| ACCUMULATE-FILTER | as ACCUMULATE, but each synthetic document must pass the fixed filter of §5; the kept set is topped up to B tokens so the regime is quantity-matched with ACCUMULATE | confirmatory |
| ACCUMULATE-SUBSAMPLE | the ACCUMULATE union subsampled (seeded) to B tokens: constant dataset size and compute | robustness priority 6 |
| REAL-REPEAT | the real seed corpus again, no synthetic text: the no-synthetic control for continual fine-tuning drift | robustness priority 3 |

## 4. Generation recipe (synthetic corpus for the next generation)

- Engine: vLLM in bfloat16 (`max_model_len` = prefix + continuation + 16); the HF `generate` path is the fallback (3–5× slower) and uses the same per-batch seeding.
- Prompts: the fixed 10,000 prefixes per language, stored as **token ids** (`prefixes_<lang>.jsonl`, 12 words ≈ 16 EN tokens, more BN tokens) and fed after the `<bos>` token, cycled in a seeded order until B generated tokens; each continuation up to the per-language cap (190 words converted to tokens at Gate 1). Prefix tokens are not counted in the budget.
- Sampling: temperature 1.0, top-p 1.0 (pure ancestral sampling); the -topp95 robustness pair uses top-p 0.95. **Every request has its own seed** (chain seed × 1,000,003 + document index), so a prefix reused within a corpus gets a fresh continuation while the corpus stays reproducible; `generate.json` records the exact-duplicate rate of continuations (bug threshold 5%), empty rate, cap-hit rate, mean length in tokens/words/chars/bytes and the engine.
- Output: `results/chains/<chain>/gen_<g>/synthetic.jsonl` with prefix, prefix ids, continuation, token count and finish reason per document.
- **Sample.** After training, every checkpoint (base, generation 0 and every generation) generates one continuation for each of the first 2,000 prefixes in file order with its own chain's sampling settings (`sample.jsonl`, seed = chain seed + 7); all sample-based metrics use this sample, on the continuation only. The 50 documents for human reading are the first 50 of this sample.

## 5. ACCUMULATE-FILTER rule (fixed; `filter_log.jsonl` records the reason per document)

A synthetic document is kept if, in this order: (a) ≥ 95% of its letters are in the target script (Bengali block / Latin script); (b) its repeated-4-gram rate ≤ 0.20 (lower-cased word 4-grams); (c) its per-token NLL under the language's generation-0 model lies within the 5th–95th percentile band of the generation-0 model's per-token NLL on the regular held-out documents truncated to the synthetic document length (length-matched band); the band is computed from the full held-out set and a scoring failure is fatal, never skipped; (d) it is not a MinHash near-duplicate (word 3-gram shingles, 64 permutations, 8 bands, estimated Jaccard ≥ 0.8) of any seed document or of any synthetic document already kept by that chain. If the kept tokens fall short of B, further documents are generated and filtered (top-up) until B is reached or 2 × B tokens have been generated; the kept set is then truncated to B tokens. `filter.json` records counts per criterion, pass rate, top-up rounds, generated tokens and any remaining shortfall.

## 6. Build validation (Gate 2) and pilot (Gate 3)

1. Base-model and generation-0 held-out log-perplexity and bits-per-byte per language are finite and generation 0 improves on the base model.
2. Generation-0 tail-fact recall per stratum is above chance (CI excludes 0.25) in both languages; otherwise the probes are rebuilt before Gate 1 closes (pre-registered floor rule).
3. The generation-0 sample is in the right script (≥ 95% of documents) with repetition < 0.2, exact-duplicate rate ≤ 5% and empty rate ≤ 5%.
4. Pilot (Gate 3): one REPLACE step per language; the authors read 50 samples each; `plan_budget.py --measured` turns the measured generation and training rates into the real projection, and the pre-registered priority order plus the approved cap decide how many robustness chains run.
